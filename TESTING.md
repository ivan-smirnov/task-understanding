# Проверка `task-understanding`

Документ отделяет проверяемые результаты от заявлений о совместимости. Не добавляйте сюда клиентские материалы, полные чаты, токены или локальные пути с персональными данными.

## Проверка локальных изменений Unreleased

Старые PASS ниже относятся только к опубликованному `v0.1.0`, а не автоматически к изменённому скиллу. Для новой проверки фиксируйте базовый commit, хэш фактически скопированных инструкций, дату, версию клиента, модель или наблюдаемый режим выбора модели, сценарий и результат. Если клиент использует `Auto` и не раскрывает выбранную модель, так и укажите; не угадывайте её.

Для воспроизводимой идентификации инструкций из корня репозитория:

```bash
shasum -a 256 SKILL.md agents/openai.yaml references/agreement-and-changes.md references/clarification-paths.md references/live-file.md | shasum -a 256
```

Не меняйте тестируемую копию скилла посреди последовательности. После исправления создайте новый временный проект; сохраните первоначальный FAIL в отчёте.

### Сквозная проверка

Полные исходные данные и последовательность находятся в `evals/evals.json` и перечисленных в нём `fixture_dir`. Копируйте в проект только скилл и исходные материалы, не критерии оценивания. Промпты клиентов не должны содержать ожидаемый ответ или предположение о номере, который агент обязан выдать вопросу.

Проведите цепочку: неполный бриф → частичный ответ → продолжение в новом чате → подтверждение конкретной редакции → первое изменение → второе изменение в новом чате → пересогласование → повтор подтверждения. Используйте фактический живой файл предыдущего шага; не заменяйте его эталоном и не возвращайте старую переписку на шагах нового чата. Допустим новый процесс на каждом шаге. Дополнительный ответ на действительно оставшийся вопрос сохраняйте как отдельный вход теста, не исправляйте артефакт вручную.

Автоматически проверяйте обязательные разделы, определения и ссылки Q-ID, сохранение закрытых решений, состояния редакции и основы, новые снимки и SHA-256 прежних. Семантическую проверку выполняет независимый оценщик по исходным запросам и полученным файлам: сохранность фактов, обоснованность вопросов, отсутствие дополнительных неподтверждённых обязательств и полнота карты проблем. Успешный выход CLI и структурная проверка сами по себе не означают семантический PASS.

Дополнительно повторите миграцию старого файла, неоднозначное подтверждение, подтверждение с открытым блокером, защиту чужого файла, prompt injection и отсутствие неявного запуска. Для Unreleased сквозной и дополнительные прогоны нужны в Codex и Cursor; Claude Code остаётся beta со статической проверкой.

### Проверка фактических артефактов

Проверяющий скрипт не запускает клиент. Установите тестируемую копию скилла только во временный проект по инструкции своего клиента. Храните записи проверки вне видимой ему папки:

```bash
test_project="$(mktemp -d)"
test_records="$(mktemp -d)"
cp -R evals/fixtures/full-lifecycle-sequence/initial/. "$test_project/"
python3 scripts/validate_artifacts.py begin-step evals/evals.json full-lifecycle-sequence brief "$test_project" --records-dir "$test_records"
# Передайте напечатанный вход клиенту в test_project; для Cursor замените $task-understanding на /task-understanding.
python3 scripts/validate_artifacts.py check-step evals/evals.json full-lifecycle-sequence brief "$test_project" --records-dir "$test_records"
```

Повторите `begin-step` → клиент → `check-step` для следующих ID из `steps`. `begin-step` сверяет перенос предыдущих файлов по SHA-256; `check-step` проверяет структуру, заданные состояния и изменения снимков. Они не доказывают открытие нового чата: это обеспечивает запускающий клиент. Дата сквозной фикстуры — `2026-09-05`; при повторе в другой день обновите `environment.local_date` и ожидаемые имена снимков в тестовой копии манифеста, не заставляйте скилл брать старую дату вместо локальной.

Отдельная проверка идемпотентного подтверждения:

```bash
python3 scripts/validate_artifacts.py live "$test_project/work/sequence/Понимание задачи.md" --project-root "$test_project"
python3 scripts/validate_artifacts.py record "$test_project" --live "work/sequence/Понимание задачи.md" --output "$test_records/before-repeat.json"
# Передайте повтор подтверждения уже сохранённой редакции тому же проекту.
python3 scripts/validate_artifacts.py compare "$test_records/before-repeat.json" "$test_project" --live "work/sequence/Понимание задачи.md" --expect-live-unchanged --expect-no-new
```

При новом согласовании вместо `--expect-no-new` укажите `--expect-new "work/sequence/<точное имя снимка>.md"` и такое же имя в `--snapshot-equals-live`. Старые снимки всегда сравниваются по SHA-256. Для проверки существования согласованной основы передавайте `--project-root` команде `live`. Автоматическая часть проверяет файловый контракт и формальные условия готовности. Смысл фактов, достаточность и зависимость вопросов оцениваются независимо по входу и выходу, а не совпадением формулировок.

Автоматическая проверка обеих цепочек: 16 из 16 шагов PASS. Проверены фактический перенос между шагами, обязательные разделы, определения и ссылки Q-ID, сохранение закрытых ID, номера редакций, имена основ, ровно два снимка в каждом проекте, SHA-256 старых снимков и неизменность живого файла при повторе подтверждения. Статические проверки рабочей копии: репозиторный и системный валидаторы, 16 self-tests, JSON и `git diff --check` — PASS. Права CI остаются `contents: read`, закреплённые SHA Actions не изменены.

Независимый оценщик читал исходные входы и реальные выходные файлы, а не только ожидаемые ответы. После исправлений существенной потери фактов или неподтверждённых условий в проверенных цепочках не обнаружено. В Cursor отмечены дополнительные формулировки вариантов решения и запись ответа о готовых таблицах рядом с решением по критериям; это не признано содержательным провалом. При проверке неявного запуска Codex использовал другой установленный скилл для текста: наличие его рабочего файла с `understanding` в имени не считалось запуском `task-understanding`.

При проверке самого eval-инструментария сопоставление фактов по подстрокам дало ложные ошибки на корректных списках критериев: формулировки находились в разных пунктах, а не в одном абзаце. Эта проверка удалена из автоматических assertions; сохранность смысла проверяет независимый оценщик по `expected.behaviors` и исходным сообщениям. Реальные файлы клиентов ради прохождения тестов не исправлялись.

Синтетические трассы остались во временных каталогах вне репозитория. В публичные документы внесены только сценарии, версии, хэши и результаты; пользовательские чаты, данные авторизации и секреты не сохранялись.

## Статические проверки

Из корня репозитория:

```bash
python3 scripts/validate.py
python3 -m unittest discover -s scripts -p 'test_*.py' -v
python3 -m json.tool evals/evals.json >/dev/null
git diff --check
```

CI запускает репозиторный валидатор и его self-tests при push и pull request. Self-tests намеренно удаляют порог готовности, обязательный раздел, повреждают ID/ссылку или старый снимок только в временных копиях. При наличии системного `skill-creator` дополнительно запустите его `quick_validate.py` для корня Skill.

Каждый прогон выполняется в отдельном временном проекте на синтетических данных.

| ID | Сценарий | Ожидаемое наблюдаемое поведение |
|---|---|---|
| `TU-01` | Явный запуск с новым неполным брифом | Создан живой файл; показана карта проблем; блокеры связаны с вопросами заказчику |
| `TU-02` | Продолжение в новом чате по существующему живому файлу | Состояние продолжено без потери подтверждённых данных и без повторного разбора с нуля |
| `TU-03` | Частичный ответ заказчика снимает блокеры, но оставляет значимые пробелы | Снятые проблемы обновлены; оставшиеся неблокирующие проблемы и вопросы всё ещё показаны |
| `TU-04` | Пользователь подтверждает постановку с открытым блокером | Снимок не создан; агент указывает конкретный блокер и нужный ответ |
| `TU-05` | В папке находится живой файл другой задачи | Чужой файл не перезаписан; агент просит выбрать или создать отдельный путь |

## Матрица релизной проверки

Для Codex выполните `TU-01`–`TU-08`. Для Cursor обязательны как минимум `TU-01`, `TU-02` и `TU-08`:

- если основной сценарий `TU-01` не проходит, релиз блокируется;
- если `TU-08` не проходит, допускаются не более двух узких корректировок описания и повторных прогонов;
- если после них негативный сценарий остаётся красным, Cursor обозначается как beta без заявления о строгом explicit-only поведении.

Claude Code в `v0.1.0` остаётся beta; до авторизации выполняется только статическая проверка пакета и совместимости frontmatter.
