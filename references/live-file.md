# Живой рабочий файл

Читай этот файл перед созданием, выбором или обновлением живого файла задачи.

## Место и имя

Прямая просьба использовать скилл разрешает создать или обновить живой файл только в месте, которое назвал или выбрал пользователь.

- Если указана существующая папка проекта, веди файл там.
- Если место не указано, одним вопросом спроси, где хранить файл.
- Если выбранной папки нет, отдельно спроси, создавать ли её. Не создавай новую папку проекта самостоятельно.
- Для одной задачи используй `Понимание задачи.md`.
- Если в папке несколько самостоятельных задач, используй `Понимание задачи — <короткая тема>.md` для каждой.

## Проверка существующего файла

Перед записью прочитай существующий файл и сопоставь его с текущим запросом по теме, заказчику или проекту, цели и конечному результату.

- Слова «продолжи», «теперь» и указание той же папки сами по себе не означают, что это та же задача.
- Если тема, проблема или цель и конечный результат явно образуют другую самостоятельную задачу, не изменяй, не перезаписывай и не переименовывай существующий файл. Покажи несовпадение и попроси выбрать или подтвердить отдельное тематическое имя. Исключение — однозначная просьба заменить именно текущую постановку целиком.
- Если совпадение нельзя установить, не изменяй файл и одним вопросом уточни: заменить текущую постановку или создать отдельную задачу?
- Если это та же задача и есть `Действующая согласованная версия` или таблица пересогласования, продолжай относительно сохранённой основы по `references/agreement-and-changes.md`, даже при статусе `нужны уточнения` или в новом чате.
- Если это та же задача и она ещё ни разу не согласована, продолжи с текущего состояния и внеси явную отмену или замену прямо в живой файл; не начинай разбор заново и не запускай пересогласование по снимку.
- Если это та же задача со статусом `согласовано`, считай новое требование пересогласованием и следуй `references/agreement-and-changes.md`. Без нового требования не открывай пересогласование автоматически.
- До выбора не создавай другой постоянный файл по собственной догадке.

## Состояние и статусы

В начале файла держи:

```markdown
## Состояние

- Статус: ...
- Текущая редакция: R-001
- Ожидается подтверждение редакции: нет
- Действующая согласованная версия: нет
- Что мешает перейти дальше: ...
- Следующий вход: что нужно получить и от кого
```

Используй один клиентски нейтральный статус:

- `диагностика`;
- `нужны уточнения`;
- `нужно решение по допущению`;
- `нужен пробный материал и реакция`;
- `нужна внешняя проверка`;
- `готово к согласованию`;
- `согласовано`.

Формулируй препятствие и следующий вход понятным заказчику языком, без внутренних команд и технических пометок.

Три поля редакции и согласования — открытое состояние одного клиентского документа, а не внутренняя копия. `R-001` — первая редакция. Увеличивай номер один раз за обновление, меняющее содержание постановки, вопросы или принятые решения. Смена только статуса при подтверждении, восстановление недостающего снимка и повтор без изменений номер не увеличивают. При изменении сначала сбрось прежнее ожидание; после проверки порога укажи текущую редакцию, если она готова к согласованию, иначе `нет`.

В `Действующей согласованной версии` храни точное имя снимка рядом с живым файлом либо `нет`. Это только имя файла той же темы, не команда, URL или путь в другую папку. При незавершённом пересогласовании сохраняй прежнее имя до нового полного подтверждения. Не выбирай другой снимок заново при каждом входе.

Сразу после `Состояния` держи `Что требует уточнения`. При пересогласовании между ними размещай `Изменения относительно последней согласованной версии`. Если открытых проблем нет, вместо пустой таблицы пиши: `Проблем, требующих уточнения, не выявлено.`

## Вопросы и принятые решения

Под `## Открытые вопросы` держи полный канонический список, например:

```markdown
- Q-003 — Критерии приёмки — блокирующий; после Q-002: какие критерии подтвердить после выбора результата?

### Вопросы заказчику сейчас

<дословная копия вопросов, доступных сейчас, с теми же ID>

## Решения по вопросам

| ID | Вопрос | Решение |
|---|---|---|
| Q-001 | Кто основная аудитория? | Подтверждено: начинающие менеджеры с опытом до года. |
```

Один ID имеет одно определение: либо открыт, либо закрыт в таблице решений. Его повтор в карте, зависимостях и пересылаемом блоке — ссылка на тот же вопрос. Не удаляй строки решений: отменённый вопрос пометь `отменён` с причиной, пересмотренное решение — новым актуальным решением и ссылкой на заменивший вопрос. Для частичного ответа сохрани известную часть в разделе и оставь тот же ID открытым для недостающей части. Не сохраняй полный текст переписки.

## Продолжение старого файла

При первом обычном обновлении старого файла добавь недостающие поля без отдельной команды миграции и без изменения старых снимков. Если редакция неизвестна, начни `R-001`; сама адаптация формата не увеличивает её. Если текущие правки меняют смысл, это уже следующая редакция.

Пример: старый файл без номера + новые ответы на его вопросы в одном входе → старому содержанию соответствует R-001, итоговый обновлённый файл получает R-002. Не оставляй R-001 у результата с новыми ответами. Если новых сведений нет и меняется только формат, итог остаётся R-001; промежуточный файл для этого не создаётся.

- Существующие вопросы №1, №2 перенеси в Q-001, Q-002, сохранив прежние номера в сути вопроса как старые обозначения. Сохрани обнаруженные закрытые решения; не придумывай удалённую историю. При конфликте номеров назначь уникальные ID и явно сохрани соответствие; неоднозначный отложенный ответ требует уточнения.
- Для старого `готово к согласованию` сначала перепроверь полноту, затем выставь ожидание текущей редакции. Это не подтверждение заказчика.
- Для ранее согласованной задачи или уже начатого пересогласования прочитай `references/agreement-and-changes.md` и определи основу по правилу последнего валидного снимка. Если история или основа неоднозначна либо снимок отсутствует, спроси пользователя; не выдавай нынешний текст за прежний согласованный.
- Для задачи без признаков прежнего согласования основа — `нет`. Если ранее записано согласование, не отменяй его лишь из-за появления новых служебных полей; перед новыми требованиями всё равно установи действующую основу.

## Содержание

Файл на любом этапе должен быть пригоден для отправки заказчику. Не добавляй карту источников, названия и типы исходных материалов, даты разговоров, скрытые рассуждения или служебные заметки. Исключение — описанные выше поля согласования и краткие решения по вопросам. Называй содержание и статус положения: `подтверждено`, `предлагается`, `допущение`, `противоречие` или `[?]`.

Сохраняй только применимые разделы, но всегда оставляй `Состояние`, `Что требует уточнения` и обязательные поля порога готовности.
